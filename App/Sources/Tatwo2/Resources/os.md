# TATWO OS 憲法（os.md v3，2026-09-05）

這份是給人看的規矩。改這份＝改 OS。機器讀的是同資料夾的 `os-upstream.md`（一頁，App 每開一條對話就交給引擎）。
六個部分，跟 App 裡「OS」頁的六個方塊一樣：上游、身份組、流程、記憶、設備、技能。

## 核心設計原則：輕量、使用效率、直觀、準確（2026-09-07，使用者明確批准）

TATWO OS 的架設、維修與優化，必須圍繞 **輕量、使用效率、直觀、準確**，並兼具穩定與可拓展性。OS 的價值是讓 AI 與使用者更直接地完成工作，不是增加管理流程。

- **輕量**：優先修補、重用既有能力；避免厚重的程式設計、重複狀態、無必要的抽象層、常駐服務與代理層。
- **使用效率**：減少等待、重查、重複輸入與確認；能由程式可靠處理的狀態，不讓 AI 反覆推理或輪詢。
- **直觀**：介面只呈現當前任務適用的狀態與操作；讓使用者清楚知道正在做什麼、是否需要介入，不必理解內部治理名詞。
- **準確**：狀態、進度、能力與成果必須符合可驗證的實際情況；不得以假完成、隱藏失敗或過期狀態換取表面順暢。
- **保留 AI 發揮空間**：避免侷限 AI 判斷與產出的死規矩；依任務需要選擇工具、實作與協作方式，不把所有工作強制套入固定派工、契約或審批流程。
- **穩定且可拓展**：以清楚、必要的模組邊界與小步可回退修改支援擴充；不為尚不存在的需求預建厚重框架，也不以減碼犧牲必要的錯誤處理、隔離與驗證。

增設流程或架構前，先確認既有能力無法解決具體問題，且收益大於操作、維護與執行成本；不得只為形式完整而增加負擔。既有規則若造成冗餘或妨礙工作產出，應提出精簡，而不是繼續疊規則。這不撤銷使用者授權、隱私、破壞性操作等必要安全邊界，也不改變已明確限定的派工權限。

來源：使用者 2026-09-07 明確要求 OS 架設與優化遵循上述原則。

## 1. 上游：OS 在所有 AI 的最上面

- 這段在管什麼：規矩由 OS 統一發，引擎（OpenAI、Anthropic、Grok，以後任何一家）只是肌肉。接新引擎只要把它接到 OS，不用重新調教。
- 入口：`入口資料夾/`。裡面的 `os.md` 是規矩，`os-upstream.md` 是每條對話開頭那一頁，`skillet.md` 是常用技能。
- 怎麼接：設定 › OS 按「把所有引擎接到 OS」。App 會在每個引擎的家（Claude 的 CLAUDE.md、Codex 的 AGENTS.md、Grok 的 GROK.md、OpenClaw 每個 workspace 的 AGENTS.md、OS 內建的三家）寫入同一段，指回入口。
- 代差怎麼防：每次開 App 比對各家那段記的版本跟 `os-upstream.md` 現在的版本，不一樣就在 設定 › OS 亮黃燈，按一下重新對齊。
- 改規矩的順序：先改 `os.md`（人看的），再改 `os-upstream.md`（機器看的），存檔後下一條新對話就生效。

## 2. 身份組

- 你＝主人。工作台是聊天：切任何模型、改檔、跑指令；唯一的管制是那條對話的權限檔位（先問我／代我核准／全權）。
- 主導＝當前對話的引擎。負責規劃、實作、按需協作、驗收、對你回報；能直接完成的工作就自己做，不為派工而派工。
- sub＝被主導派出去做一段工作的引擎（同專案下的子對話）。範圍鎖死、做完即停，不自己擴權。
- 副審＝另一家引擎讀 diff 給結論；不自審。
- 監工＝機器：活性（5 分鐘沒輸出提醒、15 分鐘沒輸出當卡死）、機器壓力（啟動卷、記憶體、負載）、範圍偏差。
- 主導負責整合與最終判斷；sub 可在明確範圍和權限內實作或審查，不限於機械工。依任務與設備壓力選擇是否並行，不增加無效等待。

## 3. 流程：釐清目標 → 執行 → 驗收（全部住在對話裡，討論與派工按需）

一般已授權工作由主導直接完成；不強制每次先開計畫、子對話或施工副本。只有使用者要求討論、工作需要協作或涉及必要安全邊界時，才走對應步驟。

| 步 | 長相 | 證據放哪 |
|---|---|---|
| 目標 | 你一句話，主導整理成右側資訊卡的一張 issue 卡 | 對話第一則＋issue 清單 |
| 討論 | `/plan`：主導在同一條對話寫白話計畫（做什麼、動哪些檔、怎麼驗、風險），**不改任何檔案**，等你說「開始」 | 對話 |
| 執行 | `/plg`：依已確認計畫開工；主導直接實作，必要時才開子對話協作。使用派工工具時，每個 sub 有明確範圍、工作副本與報告；沿用既有監工 | 對話；有派工才附子對話及報告 |
| 驗收 | 主導親自重跑（建置、測試、截圖），逐條對齊目標，做不到的明說；審查派另一家 | 對話收尾訊息＋git diff |

- `/issue`：把一個問題直接記進右側資訊卡的清單，不叫模型、不開始做。`@` 叫出清單（本串在上、全域在下）。
- 三種派工：平行（多個 sub 各自一份副本）、序列（一個做完換下一個）、副審（另一家讀 diff）。不疊監工。
- 長工作交給 App 代跑（`run_background`），不要自己在背景掛程序。
- sub 報告收完，主導回收它的工作副本（`reclaim_room`）；沒提交的改動會先保存。

## 4. 記憶：GBrain

- GBrain 是 OS 的記憶層，以 MCP 的形式掛在對話上（資訊卡勾選；需要才開）。
- 分層：raw（各系統原始產出）→ working（加工中）→ curated（蒸餾過、可重用）→ executable（可直接被程式讀的規則）→ truth（實際跑過、有數據的基線）。
- 蒸餾（`/蒸餾`）由 Claude 的對話做，不是 App 自動做；truth 只收實際驗證過的東西。

## 5. 設備

- 這台是主機。其他設備先配對（設定 › 設備：主機出 6 碼、5 分鐘、只能用一次；對方輸入主機位址＋碼），信任就是 SSH 金鑰，撤銷就是從名單拿掉。
- 遠端跟本地並行：左列同時列本機與每台已配對設備的專案與對話；點遠端對話就在那台跑；右鍵「拉到這台」「併回設備」。沒有自動雙向同步；搬東西都是你按了才搬。
- 每台只放自己在做的東西；換更大的主機不會拖累小設備。

## 6. 技能與工具

- `skillet.md`：常用技能，`$skillet` 叫出；技能根在 `入口資料夾/skills`。技能只在需要時讀，不整包灌進對話。
- MCP 由 OS 統一登記，每條對話在右側資訊卡勾選；預設只開 OS 自己的（瀏覽器橋、tatwo2_os），blender、gbrain、GitHub 需要才開。
- 三家引擎打包在 App 裡，各自登入、各自獨立的資料夾；設定 › 模型登入看得到額度、可以「禁用 API」。
- GitHub 帳號由 OS 管（設定 › GitHub）：多帳號、預設、資料夾對映、OS 代替 git 給憑證。

## 7. 硬規則

1. 拆之前先討論；封存不直刪；沒有回覆就不動。
2. 派工沒監工＝不算在跑；沉默不等於進度。
3. 驗收＝主導親驗（重跑測試、看原始輸出、看截圖）；執行者自報不算；審查派另一家。
4. 各家的權限走它自己的機制（Claude 的權限提問、Codex 的核准、Grok 的隔離），OS 只把你的檔位翻譯給它們；OS 不另造合約、收據、簽章、關卡。
5. 秘密不進摘要、文件、公開 repo；不動 API key、倉位、策略等交易面。
6. 觀測不能說謊：先驗 log 大小再看結論；跳過不算通過。
7. 條目要標來源（你的原話或證據路徑）；沒來源的待辦當作自我增生。
8. GitHub 是私人備份與回滾錨點；里程碑打帶時間戳的 tag，不 force push。
9. 任何會等網路、等子程序、等外接卷的動作，不准擋住畫面（主執行緒）。
